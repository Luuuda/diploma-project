## 1.1 Аналіз предметної області

Підрозділ буде розроблено в наступних етапах календарного плану.

## 1.2 Аналіз існуючих аналогів

Для порівняння обрано три програмні платформи електронної комерції, що представляють різні архітектурні парадигми: модульний моноліт (Shopify), моноліт (Adobe Commerce) та headless-платформу на основі мікросервісів (commercetools). Аналіз виконано з позиції інженерної системи: розглянуто архітектурний патерн, протоколи взаємодії, стек даних і механізми консистентності, а також відомі технічні обмеження.

### 1.2.1 Shopify

- **Архітектурний патерн.** Модульний моноліт (Shopify Core) на Ruby on Rails. Горизонтальне масштабування реалізовано через архітектуру pods: кожен pod є ізольованим набором шардів MySQL, інстансів Redis і Memcached та черг фонових завдань, а мерчанти розподіляються між pods. Ізоляція pods обмежує поширення відмови (blast radius) межами одного pod, проте код ядра розгортається як єдина одиниця.
- **Протоколи та взаємодія.** GraphQL Admin API і GraphQL Storefront API, REST Admin API (з 1 жовтня 2024 року має статус legacy, нові публічні застосунки з 1 квітня 2025 року повинні використовувати виключно GraphQL), Webhooks (HTTPS). Обмеження частоти запитів: алгоритм leaky bucket для REST і розрахунок вартості запиту (query cost) для GraphQL.
- **Стек даних і консистентність.** MySQL із шардингом за ідентифікатором мерчанта, Redis, Memcached, Elasticsearch для пошуку. Для потокової передачі даних використовується Kafka. Транзакції ACID гарантуються в межах одного шарда. Доставка Webhooks відбувається за семантикою at-least-once, тому споживач повинен виконувати дедуплікацію за ідентифікатором події.
- **Технічні обмеження.**
  1. Єдина кодова база ядра ускладнює незалежне розгортання та масштабування окремих доменів.
  2. Навантаження одного мерчанта обмежене ресурсами його pod, тому під час пікових розпродажів застосовуються черги та throttling оформлення замовлення.
  3. Закрита SaaS-платформа: інфраструктуру та політику лімітів API контролює вендор.
  4. Семантика at-least-once для Webhooks переносить складність забезпечення ідемпотентності на клієнтську сторону.

### 1.2.2 Adobe Commerce (Magento 2)

- **Архітектурний патерн.** Моноліт на PHP з модульною структурою (Dependency Injection, плагіни, observers). Один застосунок обробляє каталог, кошик, оформлення замовлення та адміністрування. Масштабування здійснюється реплікацією вебвузлів за балансувальником, а база даних залишається вузьким місцем.
- **Протоколи та взаємодія.** REST API, SOAP API, GraphQL. Для асинхронних операцій (Bulk API, експорт, Multi-Source Inventory) використовується черга повідомлень RabbitMQ, консюмери якої запускаються через cron.
- **Стек даних і консистентність.** MySQL або MariaDB із моделлю EAV (Entity-Attribute-Value), OpenSearch або Elasticsearch для пошуку, Redis для кешу та сесій, Varnish для full-page cache. Консистентність забезпечується транзакціями ACID в одній СУБД. У модулі Multi-Source Inventory (MSI) застосовується таблиця резервувань (reservations) із append-only записами для зменшення блокувань рядків складу.
- **Технічні обмеження.**
  1. Модель EAV породжує складні SQL-запити з численними JOIN, тому використовуються індексатори, що додають затримку актуалізації даних.
  2. Оформлення замовлення виконується синхронно в одній транзакції СУБД, що створює конкуренцію за блокування під час піків.
  3. Горизонтальне масштабування запису в MySQL обмежене (потрібні primary/replica та розділення БД).
  4. Продуктивність критично залежить від кешування (Varnish, Redis), а інвалідація кешу ускладнює експлуатацію.
  5. Значний технічний борг і конфлікти сторонніх розширень.
  6. Обробка черг через cron не забезпечує гарантованої затримки.

### 1.2.3 commercetools

- **Архітектурний патерн.** Headless-платформа за підходом MACH (Microservices, API-first, Cloud-native, Headless), що надається за моделлю SaaS. Домени (каталог, кошик, замовлення, склад) виділені в окремі сервіси, доступні через єдиний API. Незалежне масштабування доменів відбувається на стороні вендора.
- **Протоколи та взаємодія.** HTTP REST API (JSON), GraphQL API. Асинхронні повідомлення доставляються підписками (Subscriptions) у зовнішні черги та шини подій (AWS SQS/SNS, EventBridge, Google Pub/Sub, Azure Service Bus, Confluent Cloud). Для синхронного втручання у бізнес-логіку застосовуються API Extensions (HTTP-колбеки).
- **Стек даних і консистентність.** Склад СУБД і внутрішній стек публічно не розкриваються. Для запобігання конфліктам запису застосовується optimistic concurrency control через поле `version` ресурсів. Пошук і проєкції даних забезпечують eventual consistency. Доставка повідомлень підписок не гарантує строгого порядку та унікальності, тому потрібна дедуплікація на стороні споживача.
- **Технічні обмеження.**
  1. Закрита реалізація (vendor lock-in): механізми консистентності та політику відмовостійкості неможливо змінити.
  2. API Extensions виконуються синхронно в критичному шляху запиту та збільшують Latency.
  3. Пропускна здатність і ліміти API визначаються вендором.
  4. Eventual consistency проєкцій пошуку вимагає врахування затримки між записом і читанням.
  5. Вбудований механізм Saga для користувацьких процесів відсутній, тому оркестрація розподілених транзакцій покладається на клієнтську сторону.

### 1.2.5 Аналітичний висновок

Аналіз показав, що кожен із розглянутих аналогів вирішує задачу пікового навантаження в межах власної архітектурної парадигми та успадковує її обмеження. Adobe Commerce реалізує синхронне оформлення замовлення в єдиній транзакції СУБД: за моделі EAV це призводить до конкуренції за блокування, затримок індексації та обмеженого горизонтального масштабування запису. Shopify зменшує blast radius завдяки шардингу та pods, проте ядро залишається модульним монолітом із єдиним циклом розгортання, а ACID-гарантії діють лише в межах шарда. Платформа commercetools забезпечує незалежне масштабування доменів, однак механізми консистентності та відмовостійкості не підлягають налаштуванню, а синхронні API Extensions збільшують Latency критичного шляху.

Спільною властивістю аналізованих рішень є відсутність налаштовуваних гарантій узгодженості розподіленого процесу замовлення: ідемпотентність обробки подій і компенсація часткових відмов покладаються на споживача (Webhooks Shopify та Subscriptions commercetools працюють за семантикою at-least-once) або вирішуються блокуваннями СУБД (Adobe Commerce). У межах кваліфікаційної роботи ці проблеми адресуються сукупністю патернів: Transactional Outbox усуває неатомарність запису в БД і публікації події, Idempotent Consumer виконує дедуплікацію за ідентифікатором події, Choreography-based Saga з компенсуючими діями замінює розподілені блокування, а атомарне резервування залишків через Redis (Lua) запобігає перепродажу без глобальних транзакцій. Партиціонування топіків Kafka за ключем замовлення зберігає порядок подій, а горизонтальне масштабування консюмерів у Kubernetes забезпечує пропускну здатність під час піків. Вибір Go зумовлений низьким споживанням ресурсів і моделлю конкурентності на основі goroutines, придатною для мережевих сервісів із великою кількістю з'єднань.

Обраний підхід має компроміси (trade-offs): eventual consistency замість строгої, ускладнення експлуатації та налагодження розподіленої системи, потреба в спостережуваності (OpenTelemetry, Prometheus). Ці витрати розглядаються як прийнятні для критеріїв, визначених метою роботи, а саме відсутності перепродажу й подвійних списань за умов пікового навантаження.
